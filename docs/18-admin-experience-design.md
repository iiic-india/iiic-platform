# 18 · The admin experience: the design (M5)

The design M5 is built to: the new collections, session notes, certificates, privacy, the custom views, global search and Reports, open items with what is assumed, the test plan and who builds what. Written 23 November 2026 on branch `m5/foundation`, cut from `m3/core` (M3's first half), which holds the schema, the contracts in `src/lib/notes`, `src/lib/certificates`, `src/lib/privacy` and `src/lib/adminViews`, the access table and their unit tests. Sources: `05` (screens, roles), `04` (entities), `08` (privacy, certificates, security), `10` (M5), `15` (the operator's day), D-11, D-39, D-78.

**The migration.** The builders committed none: M5's migration, `m5_admin`, was generated at the join (24 November 2026) on top of M4's `m4_pipeline`, and holds only M5's tables and fields (M5 adds no job).

**Interface.** The interface pass is parked (`15`; the experience-pass memory): every view is built plain, accessible and correct with Payload's own components (its template, `Gutter`, lists, forms, buttons, `toast`, the confirm modal), with real `<table>`s, labelled fields and keyboard paths. Drag-and-drop and the D-78 stack (Tailwind, shadcn on Base UI, FullCalendar, cmdk, Recharts) come with that pass; the loaders below are written so the pass swaps only the components.

## 1. Rules this design keeps

- Every custom view, server function and route checks the user, an active account, the two-factor code and the role first, with `viewRefusal(user, view)` (`src/access/views.ts`), before it reads any input; then it reads with the user's own access (`overrideAccess: false, user`), so collection rules narrow what a role sees (CLAUDE.md #6). A read past the rules returns counts only and says why.
- Counselling stays private: session notes are their author's alone, encrypted, read-audited; no note, Map answer or message body reaches search, Reports, Today, exports, logs or a job's input (CLAUDE.md #3).
- Consent before storage: privacy requests and feedback store only what the person sent for that purpose; the consent log stays append-only as M2 built it (CLAUDE.md #4).
- Never invent a fact: the certificate's signatory, D-11's answers and every report definition IIIC has not given are placeholders or refusals, never guesses (CLAUDE.md #1). Never call a certificate a degree or diploma or imply recognition (CLAUDE.md #9; `src/lib/certificates/statement.ts`).
- Results, not thrown strings (`src/lib/result.ts`); Zod at every boundary; `server-only` for every module that reads the database or a key; times stored in UTC, shown in IST.
- Every write is in the audit log (`src/plugins/auditLog.ts`); acts with names of their own set `req.context.auditAction` (`issue-certificate`, `revoke-certificate`, `reissue-certificate`, `write-note`, `update-note`, `confirm-erasure`); reads of S3 and downloads from the private bucket write an entry of their own (`read-note`, `download-certificate`, `download-export`).

## 3. Session notes (D-11)

**The rule.** A note is written by a practitioner on a booking whose practitioner profile is their own (`booking.practitioner.staff` is the writer), and read by its author only. `VIEW_POLICY.notes` is the practitioner role; an owner who counsels holds that role too, and still reads only their own notes. Nobody else reads one: not an owner, not the operator, not another practitioner, not finance, not an export, not search. A non-author asking for a note gets `not-found`, the same answer as for a note that does not exist.

**What the owner and the operator see.** An owner sees on the People record that notes exist ("2 session notes, the latest on 4 January"), from `CountNotesForOwner`, never authors' words. The operator sees nothing of notes (`05`: operators cannot see notes). Erasure counts them in the owner's plan and deletes them.

**Encryption at rest.** `jose` 5.10.0 (already pinned) seals the body as a flattened JWE: `alg: dir`, `enc: A256GCM`, the key's id in the protected header (`kid`: the first 12 base64url characters of the key's SHA-256), and additional authenticated data `session-note|booking:<id>|author:<id>`, so a body copied to another row or author does not open. The key is `NOTES_ENCRYPTION_KEY`, 32 random bytes in base64, one per environment, in Vercel's encrypted environment variables (never in the repository; Preview and Production share a database today, so they share the key until they do not). It is optional: without it the app builds and runs, the notes panel says notes are not available, and every write or read answers `notes-key-missing`; nothing is ever stored unsealed. The database and backups hold only ciphertext; Supabase's own encryption at rest sits under it.

**Rotation.** Set the new key as `NOTES_ENCRYPTION_KEY` and the old as `NOTES_ENCRYPTION_KEY_PREVIOUS` (env refuses the previous one alone or equal to the current); notes open under either; the build's `pnpm notes:rekey` re-seals what is under the old key and logs the count; delete the previous key once a run moves none. The runbook gets the steps (`08` §9, `12` §5).

**Read auditing.** `ReadNote` writes `read-note` (entity, id, actor, IP; never words) in the same transaction before it hands the words back; if the entry fails, the read fails. Writes record `write-note` and `update-note` by name, because the sealed field is hidden from the plugin's field diff. A list of the author's notes shows dates only and is not a read of content.

**Where.** A "Session notes" panel on the booking record and on the person record, shown only to the booking's own practitioner: the dates of their notes, "Open" (one note, audited), "Add a note". No motion, no autosave (each save would be an audit entry), no browser storage of drafts. Built as `ui` fields added by `src/plugins/notesAndPrivacy.ts` (no column), calling `/api/notes/*`; a note opens by POST only. An owner's count sits on the person record the same way.

## 4. Certificates (D-39)

**Issue.** `VIEW_POLICY.certificatesIssue` (owner, operator) opens Learning → Certificates → Issue: the programme line, its details, the completion day, and recipients (people searched by name, each with the name as it should print; bulk is the same form with many rows, up to 200, or every person on an event's bookings). **Preview** fills `src/brand/templates/print/certificate.html` for each recipient (`{{certificate_statement}}` from `statement.ts`, the signatory from Settings, a sample ID and QR marked as a preview) and shows the pages; nothing is stored. **Issue** runs in one transaction: the next number of the year (the year's highest + 1, the unique ID retried on a clash), a 128-bit token (`crypto.randomBytes(16)`, base64url), its SHA-256 stored, the verify URL `<site>/institute/verify/<token>`, the QR code as SVG by `qrcode` 1.5.4 (already pinned; error correction M), the PDF rendered by M3's `src/lib/pdf/render.ts` (Playwright with `@sparticuz/chromium`, D-09), stored in the private bucket under `certificates/<year>/<certificateId>.pdf` with its SHA-256, one audit entry per certificate and the `certificate.issued` event that M6's C5 sends. A failure anywhere rolls the batch back. Refused with `signatory-missing` while Settings lacks the signatory, and `storage-missing` on a deployment without `R2_BUCKET_PRIVATE` (local and CI use a folder outside `public/`).

**The verify pages** (`src/app/(platform)/(education)/institute/verify/`, beside the existing `[...slug]`; the institute host maps to them with `src/lib/hosts.ts`): `/institute/verify` is a form for a typed ID (`typedCertificateId`: any case, spaces trimmed, check digit checked before a lookup); `/institute/verify/[token]` is what the QR opens (`verifyToken`, hashed, looked up). Each shows the ID, the status (Valid, or Revoked with its day and, for a reissue, the new ID), the name, the programme, its details, the completion and issue days, and the fixed statement. Never the reason, the person's contact details or the PDF. `noindex` (D-67), no cache for the status, the default register, rate-limited with the other public forms (M7). Unknown token or ID: one plain "No certificate matches" answer.

**Revoke and reissue** (`VIEW_POLICY.certificatesRevoke`, owner): Revoke asks for a reason and confirms (Payload's confirm modal); the verify page shows Revoked at once. Reissue revokes the old one with the reason and issues a corrected one that `replaces` it, in one transaction; the old page then names the new ID. Downloading a PDF (owner, operator) streams it from the bucket through a checked route and writes `download-certificate`.

**Wording.** The certificate says "Certificate of Completion" and the fixed statement (I-22); the admin's copy says certificate, programme, completion; never degree, diploma, university, accredited, recognised or approved (`08` §7; `/copy-check` on every string).

**As built (slice B).** The screen's acts are Next.js routes beside the download, each made into a Payload request (`createPayloadRequest`, so the two-factor strategy runs) and checked with `viewRefusal` before the body is read (`src/lib/certificates/http.ts`): `POST /api/certificates/preview`, `POST /api/certificates/issue`, `POST /api/certificates/<id>/revoke`, `POST /api/certificates/<id>/reissue`, `GET /api/certificates/<id>/pdf`, and `GET /api/certificates/recipients?q=<name>` or `?event=<id>` (people found by name, or everyone with a confirmed or completed booking on the event; id and full name only). One screen holds it all: `/admin/certificates/issue` issues, lists the latest 20, and with `?certificate=<ID>` shows one certificate with its download and, for an owner, revoke and reissue (Payload's confirm modal). `/institute/verify` is a GET form (`?id=`). **As joined (on M3).** `src/lib/certificates/wiring.ts` prints with M3's `renderPdf` (`src/lib/pdf/render.ts`, loaded on the first issue, serverless Chromium when `VERCEL_ENV` is set) after `selfContained` inlines the kit's stylesheet, fonts and logo, so the preview and the PDF show the kit's page; the tests keep their fake renderer. An issue still answers `render-failed` if Chromium fails, and nothing is kept. M3's `outputFileTracingIncludes` for `/api/**` ships the template, the kit's files and the serverless Chromium with the routes. The preview's frame inherits the admin's CSP (`font-src 'self'`), so its inlined fonts fall back to the system's there; the PDF embeds them. The private bucket's client is shared with the privacy exports (`src/lib/storage/privateBucket.ts`).

## 5. Privacy: requests, the consent log, the breach register

**Requests.** Seven kinds (`REQUEST_TYPES`). Clocks from `receivedAt` (`src/lib/privacy/requests.ts`): acknowledge within 48 hours, every kind; resolve within one calendar month in IST for a consumer complaint or privacy grievance, within 30 days for the rest (`05`, `08` §3–4). `DeadlinesFor` sets `acknowledgeBy` and `resolveBy` on create; they never move. States: received → acknowledged → verified → preparing → (erasure: awaiting owner) → closed with an outcome; withdrawal and correction may close from verified. An erasure or an export needs `verifiedAt` first (`not-verified`). Because the clocks never move, a request's kind and time received are fixed once it is recorded (a wrong one is closed as refused, "Recorded in error", and recorded again). **Erasure**: the operator prepares; `PlanErasure` lists what is deleted (the person's name, contact details and profile, notes, Map results, feedback, reviews, consents marked withdrawn by new ledger entries, what the person typed on their bookings, the name and address on invoices to an individual, their enquiries, their newsletter subscription, the access exports made for them, and their link on leads and on proposals sent to them, as `17` §9 asks) and what is kept and why (the emptied person record, which bookings, payments and the request itself must point at; bookings; invoices, payments and refunds under GST law; certificates; the privacy requests; the audit log; the ledger's entries; their suppressed addresses, so nothing is sent to them again, D-110); an operator's plan leaves out the notes count. The owner reads it and confirms (`VIEW_POLICY.privacyDecision`, typing the two-factor code into the confirming form, checked in that same request, `08` §9; a wrong code counts towards the lockout), which runs the plan in one transaction and records `confirm-erasure`. The person row is emptied in place rather than deleted: `bookings.person` and `data_requests.person` are required, so a deletion would fail or take the request with it. **Access**: `ExportPersonData` writes the person's own records as JSON and a readable page to the private store for the owner to send, after the same code; each download writes `download-export`. Session notes join it only if D-11 says so (assumed: not). The store is a folder outside `public/` locally and in CI; on a deployment it is the private bucket (`R2_BUCKET_PRIVATE`, under `privacy-exports/`, through the client the certificates use), and a Vercel deployment without the bucket answers `storage-missing`. Complaints get the copy as recorded (`complaintCopySentAt`, O7 in M6).

**The consent log.** Built in M2 (`consents`, append-only). M5 adds the Privacy view's filtered list (person, purpose, given or withdrawn, period in IST days; the latest 100 entries), each entry with its notice text and evidence (an address and browser are said to be recorded, not shown); the person record's history, newest first, is M2's `consents` join on People. No new write path.

**The breach register.** `incidents`: `certIn.dueAt` = detected + 6 h, `board.dueAt` = detected + 72 h, set on create (`src/lib/privacy/breaches.ts`); each notification's time typed as it happens. Today and the Privacy view show each open clock as time left or overdue (`ClockState`), never colour alone. **As joined:** a request received, or an incident detected, later than now (five minutes' leeway for a slow clock) is refused, since the deadlines it sets are the server's and a time ahead would push them back; an incident's detection may be corrected to an earlier time, which makes its clocks stricter.

**As built (slice C, on M3 and M4).** The loaders are `src/lib/adminViews/` (`today.ts`, `calendar.ts`, `reports.ts`, `search.ts`, `timeline.ts`, `proof.ts`, `settings.ts`), each asking `viewRefusal` before it reads anything and reading with the user's access; the views are `src/components/admin/views/`, each redirecting a visitor to the sign-in and a codeless session to the code before the loader runs, registered in the `// M5 C` blocks of `payload.config.ts` with one nav component (`ViewsNavLinks`, which also carries the `/` and Ctrl K shortcut) and the dashboard's link to Today. ## 7. Global search and Reports

**Search** (`SearchAdmin`): a query of 2–100 characters; a phone-like query is normalised to E.164 (libphonenumber-js) and an email to small letters before matching. Kinds, each with the user's own access: people (name contains, mobile or email equals; office only), bookings (reference; practitioners their own), invoices (number; owner, finance), certificates (ID; office), organisations and leads (M4, office). Never session notes, Map answers, message bodies, review texts or feedback comments. No query is logged or stored.

**Reports** (`LoadReports`): every figure in `REPORT_FIGURES` as a `ReportFigure` with its definition, period, the numerator and denominator or count, the working in words ("12 of 40 people with a confirmed session had one before") and a link to the records. Computable now: cross-path rate (people with confirmed bookings of two or more registers), proposal calls a month (confirmed `call` bookings), counselling sessions a month and return rate, revenue by application (captured payments less processed refunds, by the booking's service register, integer paise), no-show rate, the funnel from `analytics_events`. Team Map request to proposal (requests from the Team Map form in the period that have a proposal past draft) and lead response time (the median hours from a lead's arrival to `touchedAt`) are computed now M4 is joined. Waiting: course and Map figures (R2), the health strip's email, WhatsApp and uptime lines (M6, M7); each says so. A figure is text first and has its table; charts come with the interface pass.

## 10. Who builds what

Each builder branches from `m5/foundation`, touches only its own files, and adds its view's entry to `payload.config.ts` in one marked block each (`// M5 A`, `// M5 B`, `// M5 C`) so the join is mechanical. Nobody edits `src/access/policy.ts`, `src/access/views.ts`, the collections' fields or the contracts without asking the lead; hooks go in the builder's own module and are attached in one line.

- **A · Session notes and privacy.** `src/lib/notes/*` (keys, seal, notes, rekey; `pnpm notes:rekey`), `src/lib/privacy/requestMoves.ts`, `deadlines.ts`, `erasure.ts`, `export.ts`, `breachClocks.ts`, hooks for `data-requests` and `incidents` (clocks on create), the notes panel and Privacy view (`src/components/admin/notes/`, `src/components/admin/privacy/`), the runbook's rotation and breach steps, tests above.
