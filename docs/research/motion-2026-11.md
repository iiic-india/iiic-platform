# Research: the motion kit for the public website

Research snapshot, 22 November 2026. Every page, registry record and data file below was read on that date. Versions and dates come from the npm registry. Browser support comes from MDN's browser-compat-data, read as JSON from its repository, and current browser versions from each vendor's own feed. Gzipped sizes come from bundlejs (esbuild, minified and gzipped, React left out), bundlephobia's API, the vendor's own documentation, or the published file gzipped (marked "measured"); the source of each number is named. † marks a fact taken from a research pass and not re-read. Nothing was installed.

The proposal built on this is `11-experience-concept.md` §11. It becomes a decision when IIIC confirms it in `decisions.md`.

## The question

On 22 November 2026 IIIC's owner asked that the website "contain the best animations ever" and that libraries and skills be found for it.

On this site "best" is held to the rules already written:

- Motion has a purpose: it shows where something went or what changed. No decoration, no autoplaying loops, no scroll-jacking and no smooth-scroll library (`11` §2, §6). Nothing delays reading.
- Public pages: JavaScript ≤ 150 KB gzipped per page (the narrative pages carry about 140 KB today, so about 10 KB is left), ≤ 6 KB of it for the experience devices; CSS ≤ 40 KB; LCP ≤ 2 s; CLS ≤ 0.05; TBT ≤ 200 ms; Lighthouse performance ≥ 95; no third-party request (`12` §2).
- The Content-Security-Policy: `script-src 'self' 'nonce-…' 'strict-dynamic'`, no `'unsafe-eval'` and no `'wasm-unsafe-eval'` in production; `style-src 'self' 'unsafe-inline'`, so styles set from JavaScript are fine (`src/lib/security/csp.ts`, `12` §5).
- Everything works without JavaScript; under `prefers-reduced-motion` nothing moves; no layout shift; keyboard and screen-reader behaviour unchanged.
- Counselling pages, booking flows, the Map, legal pages and error pages carry no devices (`11` §2, §3.8). The 404's growing bar is the one device on an error page (`11` §5.1, D-29).
- The kit is the design system: light only, yellow only on paper or white, and the kit's motion roles: `--iiic-motion-fast` 150 ms, `--iiic-motion-base` 260 ms, `--iiic-motion-slow` 420 ms, `--iiic-ease` `cubic-bezier(.2, .7, .2, 1)`, and `--iiic-motion` per register (consultancy fast, education and default base, counselling slow, 0 ms under reduced motion) (`src/brand/css/01-tokens.css`, `02-semantic.css`).

What is already built (`src/components/experience/`): the reading bar (a CSS scroll-driven animation with a passive-scroll fallback), Flip the line (a 200 ms cross-fade and a bar that slides under the line), the sticky question, the founders' chapters (an IntersectionObserver reveal, 320 ms, 8 px), the insight titles with the bar marking the one in view, and "Take it with you". `11` §7 says no animation library.

### React's `<ViewTransition>` and Next.js 16.4

- React 19.3 (9 September 2026) made `<ViewTransition>` and `addTransitionType` stable (https://react.dev/blog/2026/09/09/react-19-3).
- `<ViewTransition>` animates only updates made inside a Transition, a Suspense reveal or `useDeferredValue`; a plain `setState` does not trigger it. It takes `enter`, `exit`, `update` and `share` classes, each keyed by transition type if wanted, and `default="none"` turns everything else off. React sets `view-transition-name` as an inline style from JavaScript, so the site's policy allows it. React does not turn animations off under reduced motion: the page's CSS must (https://react.dev/reference/react/ViewTransition).
- Next.js's guide, updated 18 November 2026: view transitions "work in the App Router with no configuration"; navigations by `<Link>`, `router.push()` and `router.replace()` are Transitions, so they animate; `<Link transitionTypes={[…]}>` tags a navigation; the browser's back and forward buttons do not animate (React skips `popstate`); the wrapper belongs in each `page.tsx`, not a layout, because a layout persists; a header stays put when it is named and its group's animation is `none`; `::view-transition { pointer-events: none }` keeps clicks working during the animation; the guide's reduced-motion rule sets every view-transition animation to zero (https://nextjs.org/docs/app/guides/view-transitions; the same guide ships in the package at https://unpkg.com/next@16.4.6/dist/docs/01-app/02-guides/view-transitions.md). The page for an `experimental.viewTransition` flag was not found in the 16.4.6 package (https://unpkg.com/next@16.4.6/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/viewTransition.md returned 404).
- In this repository: `package.json` pins `react` 19.2.9 (CLAUDE.md #7: React 19.2.x), but the App Router runs the React that Next.js carries inside it, which for Next.js 16.4.6 is `19.3.0-canary-278794d7-20261002` and exports `ViewTransition` (`node_modules/next/dist/compiled/react/cjs/react.production.js`). `@types/react` 19.2.14 declares `ViewTransition` only in `canary.d.ts`. So `<ViewTransition>` costs no new package and no new bytes, but the pin and the types should move to React 19.3 by decision (proposed in `11` §11).
- Why not the cross-document rule: every link on the site is Next.js's `<Link>`, which swaps the page inside the same document. `@view-transition` would run only on a full page load from one page of the site to another: the Map's form post that lands on a door, a link from the static 500 page, or a visitor without JavaScript. Most of those land on pages that carry no devices, and Firefox's stable release does not support it.
- Next.js 16 no longer turns off `scroll-behavior: smooth` during a route change unless `<html>` carries `data-scroll-behavior="smooth"` (`node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md`; https://nextjs.org/docs/app/guides/upgrading/version-16). Smooth in-page scrolling (`11` §7) needs that attribute, or every navigation would scroll smoothly to the top.

## 3. What fits

- **CSS and the platform carry almost everything.** Scroll-driven animations, view transitions, `@starting-style` and `linear()` are now in all three engines. They cost no JavaScript, run off the main thread, need no nonce, and stop with one media query.
- **React's `<ViewTransition>` is already in the page.** Next.js 16.4's App Router ships a React build that has it, so page-to-page transitions cost CSS only.
- **The smallest library that would ever be worth loading is Motion's.** `animate` from `motion/mini` (3.3 KB) or `motion/react` with `LazyMotion` and `m` (5.5 KB, its features loaded on demand) fit the headroom, but only on a page that needs a spring a person can interrupt, such as the Release 2 constellation. Nothing in the first pass does.
- **Everything else is too heavy, weakens the policy, or does what the site has ruled out.** GSAP and Anime.js are three times the headroom; Rive and dotLottie need WebAssembly and a policy change; Three.js alone exceeds the budget; Lenis, NumberFlow and the collections' effects are the kind of motion `11` §6 lists as not done.

## 4. Claude Code skills for motion and interface work

Installed in this environment:

- `animate`: build one animation, deciding in order whether it should move, why, with which tool, properties, curve and duration, how it is interrupted and how it leaves. Use it for each item when it is built.
- `improve-animations`: audit the motion already in the code and write a plan per fix. Use it after the first pass lands, to check it as a whole.
- `find-animation-opportunities`: sweep the interface for places that should move and reject the rest (used for `11` §11).
- `animation-vocabulary`: name an effect from a description ("the bar sliding under the line"), to brief a person or another agent.
- `emil-design-eng`: Emil Kowalski's rules for UI motion and polish (press scale, ease-out, durations under 300 ms, transitions over keyframes). Use it to review any motion change.
- `apple-design`: springs by damping and response, interruptibility, spatial consistency and reduced motion. Use it for the spring presets and anything a person can drag.
- `impeccable`: a broad design pass (critique, polish, harden, animate) on a page. Use it for a full review of one page before launch.
- `ui-ux-pro-max`: a searchable database of styles, palettes and patterns. Use it for reference only; the kit decides colour and type.
- `frontend-design`: guidance for a distinctive visual direction. Use it for new layouts, within the kit.
- `design:design-critique`: structured feedback on hierarchy and usability from a screenshot or page.
- `design:accessibility-review`: a WCAG 2.1 AA audit. Run it on each motion change, with reduced motion on and off.
- `design:design-system`: audit or extend the kit's tokens. Use it when the spring presets or motion roles are added to the kit.
- `design:ux-copy`: words for buttons and states (for example "Copied").
- `design:design-handoff`: a spec sheet with timings and states, for handing an item to another agent.
- `dataviz`: charts and the Map's constellation (Release 2), including how they move.

Also installed, from the VectorLab UX set: `vectorlab-ux-skills:motion` (duration tokens and which properties may move), `vectorlab-ux-skills:transitions` (enter and exit patterns, route changes) and `vectorlab-ux-skills:reduced-motion` (instant or opacity-only fallbacks). They overlap the skills above; where they differ from this site's rules, the rules win (under reduced motion nothing moves here, opacity included).

Not installed: Next.js's guide names a `vercel-react-view-transitions` skill (`npx skills add vercel-labs/agent-skills --skill vercel-react-view-transitions`) that teaches the patterns above. It may be worth adding before the page transition is built (nothing was installed for this research).
