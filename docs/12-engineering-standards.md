# 12 · Engineering standards

The bar the platform is built to: performance, search, security, caching, the backend and API, analytics and monitoring, code quality, accessibility, consent, policies, hosting and scalability. `01` sets the requirements, `07` the stack, `08` the law; this document turns them into budgets, checks and defaults that Claude Code applies on every pull request and that the release checks in `10` enforce. Where a tool's plan or price is quoted it is as of the research dated 30 October 2026 and 4 November 2026; re-check before relying on it.

## 1. Rendering model

| Route group | Rendering | Cache | Why |
| --- | --- | --- | --- |
| Public pages: `/`, `/framework`, `/founders`, `/organisations/*`, `/learn`, `/counselling`, `/proof/*`, `/about`, `/institute/*`, legal pages | Rendered per request (D-42) | The CMS data a page reads is cached and revalidated by tag when the editor publishes (a Payload `afterChange` hook calls `revalidateTag` for the page, its collection and the sitemap; on Next.js 16 the call takes a cache-life profile as its second argument); the HTML is not cached, because each response carries its own CSP nonce | Marketing pages never wait for the database; a traffic spike costs function time, not database load |
| `/journal/*` | Rendered per request (D-42); data revalidated on publish, and the index's every 10 minutes | Same | Same |
| `/map` (step 0), `/search`, `/404` | A light shell rendered per request (D-42); the search calls a small route handler; the route answering an address with the 404 writes its log entry on the server once the response has gone (`after()`), never the 404 page's component, which Next.js renders with every page; so the 404 waits for nothing and no endpoint is open to fill the log | — | Fast first paint; the dynamic part is tiny |
| `/book/*`, `/b/*`, `/feedback/*`, `/subscribe/confirm/*`, `/account/*` (R2) | Dynamic, server-rendered per request, `Cache-Control: private, no-store` | — | Personal and time-sensitive |
| `/admin/*` | Payload's admin (dynamic) | `no-store` | — |
| `/api/*` | Route handlers: webhooks, cron, `.ics`, PDFs, search, health, the 404 log's "Create redirect" | `no-store` unless a response is public and versioned | — |
| `/og/<slug>` (share images), `/llms.txt`, `/logo.png`, `/humans.txt`, `/.well-known/security.txt` | Generated by route handlers (§6) | At the edge with `s-maxage` of a day and `stale-while-revalidate`; a share image's address carries a hash of the page's title (`?v=`), so a new title is a new address | A page unpublished or renamed can stay in the edge's copy of `/llms.txt` for up to a day; social platforms cache an image by its address whatever the server sends |
| `/sitemap.xml` | Generated per request (`src/app/sitemap.ts`) from the CMS data cached by tag | Next.js sends `public, max-age=0, must-revalidate`; the edge keeps no copy | A page published in the admin is listed at once |
| `/robots.txt`, `/manifest.webmanifest` | Built once per deployment | Next.js sends `public, max-age=0, must-revalidate` | They change only with a deployment |

Data access is through Payload's local API inside server components and server actions (no HTTP round-trip to the app itself), with `depth` set explicitly on every query (no accidental deep population) and `select` limited to the fields the page renders. The institute domain is served by the same app through host-based routing in the request proxy (`src/proxy.ts`, Next.js 16's name for middleware): a request on an institute host is served from `/institute` (`INSTITUTE_HOSTS`).

## 2. Performance budgets

Measured on Lighthouse CI's throttled mobile profile (a mid-range Android on 4G) for the lab numbers, and in the field through Chrome UX Report data in Search Console once there is traffic. The field targets are the requirements in `01` (LCP under 2.5 s, INP under 200 ms at the 75th percentile); the lab budgets below are stricter so the field numbers hold on slower phones. Lighthouse CI runs each page three times and judges every budget on the best run, since noise on a shared CI machine only adds time (D-59).

| Budget | Public pages | Booking and account | Admin |
| --- | --- | --- | --- |
| Largest Contentful Paint (lab) | ≤ 2.0 s | ≤ 2.5 s | — |
| Interaction to Next Paint (lab) | ≤ 150 ms; a page load has no interaction, so Lighthouse CI holds Total Blocking Time to 200 ms, Lighthouse's own line for a good TBT (D-59), and INP itself is held in the field (§7, D-59) | ≤ 200 ms | ≤ 300 ms |
| Cumulative Layout Shift | ≤ 0.05 | ≤ 0.05 | ≤ 0.1 |
| Time to First Byte from India | ≤ 600 ms (pages render per request in Mumbai, D-42); Lighthouse CI holds the server's response time to it, and the time from India is held in the field (§7, D-59) | ≤ 800 ms | — |
| JavaScript, gzipped, per page | ≤ 150 KB total; ≤ 6 KB for the experience devices (`11` §7) | ≤ 250 KB (the checkout script loads only on the payment step) | not budgeted, but Payload's admin bundle is not loaded on public routes |
| CSS, gzipped | ≤ 40 KB (the kit is ≈ 11 KB) | ≤ 40 KB | — |
| Fonts on first view | ≤ 120 KB: Manrope (Latin) and Fraunces's upright face preloaded, about 90 KB together; Fraunces's italic is not loaded on the web, because no page sets it and `next/font` preloads every face of a call (D-60); the rest on demand | same | — |
| Images | AVIF or WebP through `next/image` with `sizes` set; the LCP image (if any) `priority`; hero ≤ 200 KB; no image over 400 KB, and a first view's images ≤ 400 KB together (Lighthouse CI, D-59) | same | — |
| Third-party requests | Cloudflare's analytics beacon only (deferred; only where its token is set, so CI and Lighthouse see none); Turnstile only on pages with a form, loaded on interaction | plus Razorpay checkout on the payment step | — |
| Lighthouse scores (CI gate) | Performance ≥ 95, Accessibility 100, Best Practices 100, SEO 100 | Performance ≥ 90, others 100 | — |

Rules that keep the budgets: fonts through `next/font/local` from `src/brand/fonts/` with `display: swap` and the kit's `unicode-range` subsets; no font loaded from a third party; the kit's CSS imported once in the root layout; page CSS in CSS modules or a single per-route stylesheet, never inline `<style>` per component; no client component unless it has state or an event handler, and no client component imports a server-only module; `next/dynamic` for the booking calendar and the admin-only widgets; `content-visibility: auto` on long pages; no layout work in `useEffect`; width and height on every image and iframe; `fetchpriority="high"` on the one asset that matters above the fold; `rel="preconnect"` only to origins the page will use in the first seconds. Lighthouse CI's resource summary (`lighthouserc.cjs`) fails a pull request when a page on its list passes the JavaScript, CSS, font or first-view image budget above; a public page joins the list when it is built (D-45, D-59). The 10 KB growth check went with `size-limit` (D-45).

Vercel's image optimiser counts source images; keep the number of distinct images small (the CMS's media library is the source) and review the usage line in the monthly cost check (`14` §4); if it ever drives cost, switch the `next/image` loader to Cloudflare Images without changing components.

## 4. Caching and data

- **Cache** for page data and generated assets: pages render per request (D-42), the CMS data they read is cached by tag, and generated assets are cached at the edge (Vercel's CDN); on-demand revalidation by tag from Payload hooks so an editor's change is live within seconds without a rebuild; a scheduled revalidation every 10 minutes for indexes as a safety net. The redirects are read as one table (at most 2,000), cached under the redirects' tag and the pages' (a redirect to a page follows its address) and read again every 10 minutes, so an address with no page is answered without the database being asked.
- **Images**: `next/image` with a long `minimumCacheTTL` (a month); media files are served from the public R2 bucket's own address, `media.imagecatalysts.in` (D-46), which the CSP's `img-src` allows (§5); file names include a content hash so they can be cached as immutable. Journal articles draw images from the media library inside their bodies (alt text required; `src/lib/journal/images.ts`): `next/image` at the column's `sizes`, lazy, with width and height; only an image of the media collection, from Payload's file route (`/api/media/file/`) or the public bucket's address, never a private bucket. `next.config.ts` gives `next/image` those two sources (`images.remotePatterns` from `R2_PUBLIC_BASE_URL`) and a month's `minimumCacheTTL` (`src/lib/media/nextImages.ts`), and each media file is named with the first 12 hex characters of the SHA-256 of its content (`src/lib/media/fileNames.ts`).
- **Database**: Supabase's connection pooler in transaction mode from serverless functions, with a small pool per function instance (`max` 3–5; 3 now; a 5-second limit on waiting for a connection, so a starved request fails instead of hanging) and `statement_timeout` set on the app's database role (15 s, applied after the migrations on every deployment by `pnpm db:settings`, because the transaction pooler ignores session settings); indexes on every foreign key and on the columns the booking engine filters (practitioner, start, status); the slot exclusion constraint (`04` § Rules the schema enforces) guarantees no double booking; `EXPLAIN ANALYZE` checked for the booking, Today and Pipeline queries before M3 and M5 ship; no query without a limit.
- **Jobs**: the queue table is indexed on `(status, run_at)`; the cron runner takes a bounded batch and finishes well inside the function's `maxDuration`; long work (PDFs, resyncs) is split into steps.
- **Sessions and holds**: slot holds and one-time codes live in Postgres with expiries and are swept nightly (O5); no Redis unless a measured need appears.
- **Client**: no client-side data cache library for public pages; server components fetch once per request; forms use server actions with progressive enhancement (they work without JavaScript).

## 5. Security hardening (in addition to `08` §9)

| Area | Standard |
| --- | --- |
| Headers | `Content-Security-Policy` with per-request nonces (set in the request proxy, `src/proxy.ts`; every HTML route renders per request, D-42) and `strict-dynamic`; `default-src 'self'`; `script-src 'self' 'nonce-…'` plus Cloudflare's beacon (`https://static.cloudflareinsights.com`, with `connect-src https://cloudflareinsights.com`, named only on public pages and only where `NEXT_PUBLIC_CF_WEB_ANALYTICS_TOKEN` is set; the script carries the request's nonce, `src/lib/analytics/beacon.ts`), Turnstile and, on the payment step only, the Razorpay origins its checkout documentation lists; `style-src 'self' 'unsafe-inline'` (Payload's admin injects styles at runtime; inline styles cannot run code); `frame-src` only Turnstile and Razorpay, and `'self'` in the admin, whose live preview frames the site (OS-4); `connect-src 'self'` plus the same; `img-src 'self' data: blob:` plus the R2 public bucket; `font-src 'self'`; `object-src 'none'`; `base-uri 'self'`; `form-action 'self'`; `frame-ancestors 'none'`, except a draft-mode response to staff signed in with their two-factor code, which the admin's live preview frames: `frame-ancestors 'self'`, `X-Frame-Options: SAMEORIGIN` and `X-Robots-Tag: noindex`, decided in the proxy from the draft-mode cookie, the session cookie and a two-factor cookie whose token verifies (`src/lib/preview/frame.ts`; the page decides again whether to draw a draft, OS-4); `upgrade-insecure-requests` (over HTTPS only; locally and in CI it would send the page's own requests to an https nothing serves). Under `next dev` only, `script-src` also allows `'unsafe-eval'` for React's debugging. The proxy runs on every path except `/api` and Next.js's own build assets, and skips nothing on a request header. Build assets carry `default-src 'none'; frame-ancestors 'none'` instead, so a missing one renders a 404 in which nothing can run. Requests for Next.js's prerendered error pages and its internal pages (`/_app`, `/_document`, `/_error`) are served the site's own 404, with the nonce. `X-Frame-Options: DENY` backs up `frame-ancestors` for older browsers: the proxy sets it with the policy, and `next.config.ts` sends it only where the proxy does not run (`/api/…`, `/_next/static`, `/_next/image`), so no response carries two values. `Strict-Transport-Security: max-age=63072000; includeSubDomains` at launch, `preload` submitted after a month without incident. `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` (`no-referrer` on the owner setup link, whose query carries its token, D-41), `Permissions-Policy` denying camera, microphone, geolocation, payment (except the payment step), `Cross-Origin-Opener-Policy: same-origin`, relaxed to `same-origin-allow-popups` on the payment step if Razorpay's checkout needs `window.opener` for bank or UPI pop-ups (verify against its documentation in M3). Payload's colour-scheme client hints (`Accept-CH`, `Vary`, `Critical-CH`) are dropped: the admin is light only, and `Critical-CH` would make Chrome send a first visit's request twice. A Playwright test asserts the headers on every route group, that every script the server renders carries the nonce, and that pages and the admin run without a CSP violation |

## 6. Backend and API

- **Boundaries.** Public inputs are validated with Zod schemas shared between the form and the server action; server actions return typed results (`{ ok: true, data } | { ok: false, error: { code, message, fields? } }`), never thrown strings; every error has a stable `code` the UI maps to copy from VOICE.md.
- **Route handlers** exist only for things that are not pages: webhooks, the cron runner, `.ics` files, PDFs, search, the answer to Find your path (`/map/go`, the target of a form that needs no script, `03` F1), the owner setup link (`/api/owner-setup`, D-41), `/api/health` (returns 200 with a database round-trip and nothing else; UptimeRobot polls it, so it is public by design: it checks no user and answers only the status, whether the database responds and the commit), the public generated files (`/llms.txt`, `/humans.txt`, `/.well-known/security.txt`, `/logo.png`, the share images at `/og/<slug>` and the sitemap; public by design, §1 and §3), and the Google Calendar notification endpoint. The 404 log has no route handler: the route answering an address with the 404 writes it on the server (§1). Each declares `maxDuration` and `runtime` explicitly.
- **Domain events** are written in the same transaction as the state change (an outbox row), and the job runner turns them into jobs; a job is idempotent by `(event id, automation id)`; retries follow `06`.
- **Money** is integer paise everywhere; prices carry a history; tax is computed on the server with the CA's classification (I-29).
- **Time** is UTC in the database and the API; Asia/Kolkata only at the edge of rendering; the booking engine works in the practitioner's time zone (always Asia/Kolkata for now) and tests cover the daylight-saving-free but 30-minute-offset arithmetic.
- **Idempotency keys** on booking submission and payment-link creation, so a double tap never books or charges twice.
- **Logs** are structured JSON with a request id, the route, the role (not the user's name), timings and an error code; never a body, a note, an answer, a full phone number or email (`CLAUDE.md`). Payload's own request logging is set to the same rule.
- **Migrations** are generated, reviewed and committed; production runs migrations only through the deploy step; never `push` in production. Rolling back `20261121_094426_review_fixes` needs every page fact that cites the registration form (source `form`, in `pages_facts` and `_pages_v_version_facts`) changed or removed first: its generated down migration recreates the facts' source type without that value, and the cast fails on any row that still has it.
- **Tests** as in `10` § Quality and testing; the booking engine, consent and access rules have property-style tests over generated inputs.

## 9. Accessibility (WCAG 2.2 AA, in addition to `01`, `10` and the kit)

## 10. Consent, cookies and tracking

- **What sets a cookie at launch:** Payload's admin session cookie (only on `/admin`); the staff two-factor cookie (`payload-totp`, set when a staff member enters their code, HttpOnly, SameSite=Lax, as long as the session, removed at sign-out); Better Auth's session cookie (R2, only after sign-in); Turnstile's ephemeral token on pages with a form (no persistent cookie; strictly necessary); the owner setup cookie (`iiic-owner-setup`, ten minutes, sent only to `/api/users/first-register`, set only while the owner setup link is in use, D-41); Next.js's draft-mode cookie (`__prerender_bypass`, HttpOnly, SameSite=None and Secure in a build, for the browser session only), set by `/api/preview` only for staff who may read drafts and have entered their code, removed by `/api/preview/exit` (the preview notice's "Leave preview") and at sign-out (OS-4); nothing else. Razorpay's checkout runs on its own origin on the payment step. Cloudflare Web Analytics, Sentry and UptimeRobot set none. A Playwright test lists the cookies set on each route group and fails when a new one appears.
- **Therefore no banner at launch** (D-14): the privacy notice has a "Cookies and similar technologies" section that lists exactly these, with purpose and duration.
- **The consent gate is built anyway** (D-30), so adding a marketing pixel later (Meta or LinkedIn for B2B campaigns) is a content change, not a rebuild: a `<ConsentGate purpose="marketing">` component that renders its children only after a recorded consent; a `consent` cookie (first-party, one year, the purposes consented to and the notice version); a banner component from the kit with two buttons of equal weight ("Yes, allow" / "No, thanks"), no pre-ticked purposes, a link to the notice, and the choice changeable from the privacy page; the `Sec-GPC` header is honoured as a decline. No pixel is added without a decision recorded in `decisions.md` and the notice updated; under the DPDP Rules (duties from 13 May 2027) tracking consent must be specific and withdrawable, and the gate already works that way.
- **Children**: no marketing for under-18s, and no analytics events about a person once the age band captured in booking or the Map says they are under 18 (`08` §3); enforced by that age band, not by the gate. The step-0 event (§7) is written before any age is known, so it may count visitors under 18: it holds the answer, the page, the time and the day's pseudonymous session code, and whether that meets the children rule is for the lawyer to confirm (I-22).

## 13. Scalability

The platform is small by design and stays cheap by caching what public pages read (D-42). What grows, and what to do when it does:

| Growth | What strains first | Response |
| --- | --- | --- |
| Traffic × 10 (a viral article, a campaign) | Function time for page renders (their data is cached, so the database is not touched); the booking functions and the database pool | Vercel scales functions; raise the pooler's pool size and Supabase compute one step; the exclusion constraint (`04`) keeps bookings correct under concurrency (tested in M3) |
| Bookings × 10 | WhatsApp and email volumes (provider rate limits), Google Calendar API calls (quota is generous), job throughput | Batch the resync (B14), keep jobs small; Resend Pro; the WhatsApp provider's next tier; nothing architectural |
| Practitioners × 10 | Calendar watch channels and working-hours screens | Channels are per calendar and renewed by B14; the admin calendar filters by practitioner |
| Content × 10 | Nothing at build: pages render per request (D-42) | Page data is revalidated on demand; the sitemap is paginated past 1,000 URLs |
| The Map and Team Maps (R2) | Compute is trivial; the aggregate is computed by a job | — |
| A second language | Routes and strings | `[locale]` segment with strings externalised from M1 (`01`) |
| The institute domain (R3) | Host routing | Already in the request middleware |
| A second product line or a team of operators | Roles and the admin's custom views | Payload's access rules scale; the audit log already exists |

What would justify a bigger change, and only then: a hand-built admin (if Payload's views cannot express a workflow IIIC needs daily), a queue service (if jobs exceed what minute-cron handles), Postgres partitioning (never at this scale). Vendor exits are kept open: Postgres dumps, R2's S3 compatibility, React Email templates that work with any sender, Payload's MIT licence, and the domain and DNS in IIIC's hands.
