# Security review · OWASP ASVS 5.0, level 2

The review M7 asks for (`10` M7; `12` §5, Review): authentication, session management, access control, input handling, and logging and error handling, checked against the code on branch `m7/hardening` (from `main` at 52e0590, M1 to M5 merged) on 24 November 2026. Each area says what was checked, what was found already in place, what was fixed in this pass and what is left, with its owner. Run it again after any change to these areas (`12` §5).

How it was checked: every route handler under `src/app/**/route.ts`, every Payload endpoint (`endpoints:` in the collections and the config), every server action (`'use server'` files), every custom admin view and every server-rendered admin panel was listed, and each was read for the order of its checks (the user, an active account, the two-factor code and the role before any input or database read), for the parsing of its input and for what it logs. Every logging call (`payload.logger`, `console`, Sentry) was read for what it can carry. The headers and the cookie inventory were compared with `12` §5 and §10. `pnpm audit` was run.

## Findings and what was done

### Fixed

1. **Errors that left a handler were logged whole (V16, medium).** Payload logs any error that escapes an endpoint or a REST operation as `{ err }`, and Next.js logs an uncaught error from a route handler or a server action. A failed database query's error carries the values it was given: its message ends with `params: …`, the same values are on the error, and Postgres's `detail` on its cause names a duplicate value. A constraint error or a time-out during a booking would have put a name, an email and a mobile number in Vercel's logs. Fixed: Payload's logger now writes structured JSON (`12` §6) with an `err` serializer that keeps only the error's name, code, status, a message with query values, emails, phone numbers and tokens cut out, and the stack's frames without its first line, for the error and two levels of cause (`src/lib/monitoring/logSafety.ts`, `src/payload.config.ts`). The booking flow's submission, reschedule and cancellation, and the certificate and invoice routes, catch a fault, log its name only, report it to Sentry through the scrubber and answer that nothing was done (`src/lib/bookingFlow/actions.ts`, `src/lib/monitoring/routeFaults.ts`). Tests: `tests/unit/logSafety.spec.ts`.
2. **A calendar feed's token could reach Sentry (V16, low to medium).** The private feed's token is 22 characters, shorter than the scrubber's 32-character rule, and its path was not among the keyed paths; a fault before the route's `try` would have sent the live token with the request's path. Fixed: `/api/calendar/feed/<token>` joins the keyed paths in `src/lib/monitoring/scrub.ts`, and the route's request is made inside its `try`. Test: `tests/unit/logSafety.spec.ts`.
3. **Input read before the role check (V8, low).** The notes routes read their query or body, and the audit-log export its body, before the module behind them refused. Nothing was used before the refusal, but a refusal should cost nothing. Fixed: both check the user, the code and the role first (`src/lib/notes/endpoints.ts`, `src/lib/adminViews/endpoints.ts`). Tests: `tests/unit/notesEndpointsOrder.spec.ts`, `tests/unit/adminViewsAccess.spec.ts`.
4. **Route ids checked by type only (V2, low).** "Reset two-factor" and the 404 log's "Create redirect" passed any string id to the database, which failed and took the error path of finding 1. Fixed: both parse a whole number first. Tests: `tests/unit/resetTwoFactor.spec.ts`, `tests/unit/createRedirectFromMissing.spec.ts`.
5. **Public booking without abuse controls (V2, medium).** The booking flow's submission had no rate limit and no Turnstile, and it, the reschedule and the cancellation would have written to production's database from a preview deployment. Fixed (D-108, recommended for IIIC to confirm the numbers): refused on a preview; Turnstile where both keys are set; on production 5 bookings an hour per address and 3 a day per email, counted from what each booking already stores. Tests: `tests/unit/bookingGuards.spec.ts`.
6. **Certificate IDs could be walked quickly (V2, low).** An ID is a year, a number and a check digit. The page already shows only initials by ID (D-96); it now also answers at most 120 lookups a minute per server (D-109). Test: `tests/unit/certificatesVerifyPages.spec.tsx`.
7. **A password reset could flood a staff mailbox (V6, low).** Payload's default allows one reset email per account every 15 seconds; now one in five minutes, answered alike either way so no account is revealed (D-109). Test: `tests/unit/resetEmail.spec.ts`.
8. **A staff check of a proposal counted as the client's view (business logic, low).** Opening a proposal's PDF signed in as staff, or on a preview, moved it to "Opened by the client". Fixed: such an opening counts nothing (`src/lib/pipeline/proposal/viewCounts.ts`). Tests: `tests/unit/pipelineProposalPage.spec.tsx`, `tests/int/pipelineProposals.int.spec.ts`.
9. **The reviews import printed raw database errors (V16, low).** `pnpm import:reviews` printed a failed row's messages, which for a database fault are the raw message with its values. Fixed: scrubbed before printing (`src/scripts/import-reviews.ts`).
10. **The `.ics` route declared no runtime or time limit (`12` §6, nit).** Fixed.

## The 404 without JavaScript

`11` §5.1 notes that a 404 raised while a page renders per request is sent as an empty document (`<html id="__next_error__">`) that the page's script fills. This pass checked why, in Next.js 16.4.6's own code: a `notFound()` thrown in a page that renders per request escapes the server's HTML render, because React draws error boundaries, Next.js's not-found boundary among them, only in the browser. Next.js then sets the 404 status and sends that empty shell with the not-found page in its data for the script to draw. Next.js draws a not-found page on the server only for its own `/_not-found` route, which it uses when no route matches an address; here every address matches a catch-all route that asks the CMS whether a page exists. The page cannot set a 404 status without throwing, and the request proxy cannot know whether a page exists without the database.

Ways out, none taken without IIIC's word: (a) the request proxy asks a small cached list of served addresses and rewrites a miss to a route that draws the 404 on the server, at the cost of a second source of truth for what exists; (b) keep the behaviour and wait for Next.js to draw not-found boundaries on the server; (c) draw the 404's content with a 200 status and `noindex`, which `11` §5.1 and D-29 rule out. The recommendation is (b) for launch, since the status, the `noindex` header and the log are right and only a browser without JavaScript sees an empty page, and (a) if IIIC wants the content without a script before Next.js changes.
