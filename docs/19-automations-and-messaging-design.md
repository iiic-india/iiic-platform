# 19 · Automations and messaging: the design (M6)

The design M6 is built to: the job runner, the messaging core, the provider webhooks, the templates, every Release 1 automation with its trigger, timing, channel and consent, re-planning, the newsletter, the digests, the tests, and who builds what. Written 23 November 2026 on branch `m6/foundation` (from `m3/core`), which holds the collections, the access rules, the contracts in `src/lib/messaging`, `src/lib/automations` and `src/emails`, the send policy, the email frame, the fakes and their unit tests. The target is M6's "Done when" (`10`): each automation has a test that proves it fires once, at the right time, to the right channel, and respects consent and quiet hours; rescheduling re-plans reminders. Sources: `06`, `13`, `07` (Resend, AiSensy, Vercel Cron, no autoRun), `08` §3, §7, `04` (messaging entities), `16` §9 (the events), D-06, D-10, D-21, D-24, D-47. Where this document and those differ, they win, and this one is corrected.

## 1. Rules this design keeps

- An automation fires once: its jobs are queued once per event key, its message is one row per unique key, and the row is claimed before the provider is called (§2). Every task is named by its automation ID and is idempotent (CLAUDE.md, Conventions).
- Consent and quiet hours are checked when a message is sent, not only when it is planned, from the ledger and the settings as they are then (§3). Promotional messages need the matching consent (`marketingEmail`, `marketingWhatsapp`) and never reach anyone under 18; transactional ones go to anyone who booked or asked (`06`, Engine rules).
- Counselling is private: events and job inputs carry ids only; a message row holds who, what about, when and its state, never a body, an address or anything said in a session; no counselling message carries an offer, and every message to the client about a counselling booking, its money included, carries the scope statement and the crisis numbers (CLAUDE.md #3, #9; `08` §7; `06`). Logs hold automation ids, template keys and outcome codes only.
- No price in any message while `prices_public` is off, except the person's own payment (§7; D-21, D-24). No dark patterns: no urgency words, no pre-ticked anything, unsubscribe in one click.
- Everything builds, runs and tests without Resend, AiSensy or the cron secret: each channel answers `not-configured` and the message falls back or is skipped, visibly (§3).
- Every route and admin action checks the user, the role and the two-factor session first, or its own secret (CLAUDE.md #6). The interface pass is parked: every admin view in M6 is plain Payload (lists, forms, buttons that work from the keyboard), accessible and correct; drag-and-drop and D-78's component stack come later.
- One migration, `src/migrations/20261124_100324_m6_messaging.ts`, generated after M3, M4 and M5 were merged (the six collections, the `people` fields, `payload-jobs`' concurrency key and every M6 task slug, `messages.subjectCollection` with `enquiries`, and the `payload-jobs-stats` global that scheduling adds); never edited by hand.

## 2. The job runner

**The route** (builder A): `GET /api/cron/jobs`, Node runtime, `maxDuration` 60 s, region `bom1`. It answers 503 while `CRON_SECRET` is unset, 404 on any Vercel deployment but production (previews share production's database, so a preview never runs a job or sends a message), and 401 unless `Authorization: Bearer <CRON_SECRET>` matches, compared in constant time over SHA-256 digests. Then it releases the jobs a stopped run left `processing` (untouched for 5 minutes, far past the function's 60 s; `src/lib/automations/staleJobs.ts`): Payload never picks a processing job again, queues no scheduled task while one waits, and lets nothing else with its concurrency key run, so one killed dispatch would stop the dispatcher for good. A released job runs again as a retry and counts as its automation's failure; once released more times than its task may retry, it is stopped with an error, which O3 counts, and `automation.failed` is raised. Then: `payload.jobs.handleSchedules({ allQueues: true })`, which queues each scheduled task whose cron has come due once per slot (Payload's `payload-jobs-stats` global); then `payload.jobs.run({ allQueues: true, limit: 25 })` in rounds until the queue is empty or 45 s have passed. It answers counts only. `jobs.autoRun` is never set (`07`). Owners keep running a task by hand through Payload's jobs API with their code (`ownerWithCode`).

**Vercel Cron**: `vercel.json` gains `"crons": [{ "path": "/api/cron/jobs", "schedule": "* * * * *" }]`. The Hobby plan allows only daily crons and refuses a deployment with this one, so the entry lands with the move to Pro (D-04; proposed, §10); until then an owner runs the queue by hand.

**Schedules** (`src/lib/automations/schedules.ts`, applied in `src/jobs/index.ts`, UTC with seconds; India is UTC+05:30 all year): `messages-dispatch` and `B4-expire-holds` every minute; `B2-poll-pending-orders` every 5 minutes; `B14-refresh-busy-times` every 15; `B11-reconcile` 23:00 IST; `O5-purge-missing-pages` 02:00 and `O5-retention` 02:15; `O1-daily-digest` 08:30; `O2-weekly-report` Monday 09:00; `O6-backup-check` 09:30; M4's `P3-P4-lead-alerts` hourly and `P8-expire-proposals` 00:10; `P6-proposal-follow-up` 08:45. M3's and M4's tasks gain their schedules here without their files changing.

**Concurrency**: `jobs.enableConcurrencyControl` is on. `messages-dispatch` takes the exclusive key `messages-dispatch`, so overlapping cron calls never run two dispatchers; each listener task takes its event key. A dispatch takes no new message after 30 s (`DISPATCH_BUDGET_MS`), so with the provider's 15 s timeout on the message in hand it ends inside the function's time; the next minute takes the rest. A task that plans many messages (N4) plans them for the dispatcher only (`queueOnly`) and sends none itself. Payload claims a job before running it.

**Retries and failure**: every M6 task has `retries: { attempts: 3, backoff: exponential from 60 s }` for faults (the database or a module throwing). A provider's refusal is an answer, not a fault: the message itself is retried after 1 minute, 10 minutes and 1 hour (`RETRY_DELAYS_MS`, `src/lib/messaging/states.ts`), then marked `failed` and `message.failed` is emitted. A task that spends its retries calls the shared `onFail` (builder A, `src/lib/automations/failures.ts`), which adds to the automation's failure count and emits `automation.failed`. O3 listens to both (§9).

**Fires once, in three layers**: (1) `emit` (booking events, `src/lib/booking/emit.ts`, now with M6's listeners read from the catalogue) and `emitAutomationEvent` (every other event, `src/lib/automations/emit.ts`) queue one job per subscribed task with the key `<event>:<id>`, in the caller's transaction, and never a second while one waits; (2) `deliver` writes one `messages` row per key `<automation>:<collection>:<id>[:<variant>]:<channel>` (`messageKey`, unique), and a key already there returns that row; (3) a due row is claimed with a conditional update (`status queued → sending` where it is still queued and due), committed before the provider is called. Resend gets the key as its `Idempotency-Key`, so a crash between its answer and the row's update cannot send twice within 24 hours: the dispatcher's sweep puts an email row left `sending` for 5 minutes back in the queue (while it has tries left). AiSensy has no such key, so a WhatsApp row left `sending` for 5 minutes becomes `unknown`, is never resent on its own, and shows on Today (at most once rather than twice). `deliver` called inside a caller's transaction writes the row and leaves the send to the dispatcher (within the minute), since the claim must commit before the provider is called.

## 3. The messaging core

**Collections** (access in `src/access/policy.ts`, audited by the audit plugin; tests `tests/unit/messagingAccess.spec.ts`):

| Collection | Holds | Read · write |
| --- | --- | --- |
| `messages` | The outbox and log (`04` `message_log`): dedupeKey (unique), automation, template, variant, channel, fallback, kind, sender, status, skipReason, lastError (a code), recipientKind with person, subscriber or staff, subjectCollection and subjectId, counselling, fallbackOf, sendAt, sendBefore, requiresOpenWindow, attempts, claimedAt, sentAt, deliveredAt, readAt, provider, providerMessageId (unique) | owner, operator · server; kept one year (O5) |
| `message-templates` | Per key, channel and language: subject, preheader, body with `{{variables}}`, for WhatsApp the provider's template name and category; status (draft · submitted · approved · rejected · paused, set by an owner), owner, lastReviewedAt; versions | owner, operator, editor · owners delete |
| `automations` | One row per catalogue entry: key, enabled, note, lastRunAt, successCount, failureCount (server) | owner, operator · they pause and resume; rows are the server's |
| `suppressions` | channel, address (unique together), reason (hard bounce · complaint · WhatsApp stop · manual), at, source, person, note | owner, operator · server and the office add; owners lift |
| `subscribers`, `newsletter-issues` | §8 | §8 |

`people` gains a join to its suppressions and `whatsappLastInboundAt` (server-written, the 24-hour window).

**States** (`src/lib/messaging/states.ts`): `queued → sending → sent → delivered → read`; `sending → queued` (a retry), `failed`, `unknown`; `sent → bounced | complained | failed` from the provider; `queued → skipped | cancelled`; staff may queue a `failed` or `unknown` message again from the log. Moves only along the table, by conditional update.

**Kinds** (`src/lib/messaging/types.ts`): `transactional`, `promotional`, `operator` (sent by a staff action about the person's own record: V1, B13) and `internal` (to staff).

**Senders** (`src/lib/messaging/channels.ts`): `EmailSender.send` and `WhatsAppSender.sendTemplate`, each returning a `Result` with the provider's message id or a coded `SendError` (`retryable` for `unavailable` and `rate-limited`). Builder A writes `resend.ts` (Resend's REST API with `fetch`, the key as `Idempotency-Key`, tags with automation and template, open and click tracking off on `notify.`) and `aisensy.ts` (the campaign API, one approved template per call), and `channelsFor(env)`: `MESSAGING_TRANSPORT=fake` gives `FakeEmailSender` and `FakeWhatsAppSender` (local, CI; refused on Vercel by `env.ts`), a Vercel deployment other than production and missing keys give `not-configured`. Payload's own email adapter stays for staff mail (D-47).

**Identities** (`src/lib/messaging/senders.ts`, `docs/13` §1, §3): `IIIC Bookings <bookings@notify.<MAIL_DOMAIN>>` replying to `bookings@`, `IIIC <hello@notify.…>` replying to `hello@`, `IIIC Platform <platform@notify.…>` with no reply address, `IIIC Journal <journal@news.…>` replying to `hello@`. Without `MAIL_DOMAIN`, everything goes from `EMAIL_FROM_ADDRESS`.

**`deliver(req, planned)`** (contracts in `src/lib/messaging/operations.ts`): checks the template allows the channel, writes the row (or returns the existing one), sets `counselling` when the subject is a booking of a counselling service, and, when it is due, tries it after the row commits. **`dispatch(req, now, limit)`**, run by `messages-dispatch` every minute: picks due `queued` rows by `sendAt`, moves stale `sending` rows to `unknown`, and tries each. **A try**: read the recipient's address now (never copied into the row); read the suppression list, the ledger (`consentFor`) for promotional mail, the age band, the automation's switch, the channel's set-up, the WhatsApp template's approval, the 24-hour window and the quiet hours (`readQuietHours`); ask `decideSend` (`src/lib/messaging/policy.ts`, pure, tested): `send`, `defer` (WhatsApp in quiet hours: `sendAt` moves to the window's end), `fallback` (a new email row with `fallbackOf`, key `…:email`) or `skip` with its reason. To send: `load` the template's data (§7), which answers `stale` if the subject changed; refuse a price the registry does not allow (`priceAllowed` with `getFlags`); render; add `List-Unsubscribe` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` to promotional mail; send; record `sent` and the provider's id, or a retry, or `failed`. Quiet hours bind WhatsApp only; a reminder they would push past its session is dropped (`quiet-hours-late`), not moved to email (`06` B6), and only when it is due, under the quiet hours then in force: planning moves a message to the window's end when that is in time and otherwise queues it for its own time (`queueTiming`). A paused automation's due messages are skipped as `paused`. Internal templates go to staff accounts only, and nothing else does. **Queue again** (`POST /api/messages/:id/queue-again`, `src/lib/messaging/requeue.ts`): an owner or the office with their code moves a `failed` or `unknown` message back to `queued`, due now with its tries counted afresh, audited; the state table has no move out of `skipped`, so a message skipped while its automation was paused cannot yet be queued again (proposed, §10).

## 4. Provider webhooks

**Resend** (`/api/webhooks/resend`, builder A): raw body up to 64 KB, verified with `svix` (`svix-id`, `svix-timestamp`, `svix-signature`, five minutes' tolerance) against `RESEND_WEBHOOK_SECRET`, then `parseResendEvent` (`src/lib/messaging/webhooks.ts`). `delivered` and `failed` move the message; a permanent bounce or a complaint moves it to `bounced` or `complained` and suppresses the address Resend tried (`suppress`, unique per channel and address), emitting `message.suppressed` for O9 and N3; a transient bounce marks the message `failed` with `soft-bounce` and suppresses nothing. Answers: 503 without the secret, 404 on any deployment but production (previews share its database; checked before the body is read), 401 bad signature, 400 unreadable, 200 for types not taken and unknown ids, 500 on a fault (Resend retries). Nothing of the body is logged.

**WhatsApp** (`/api/webhooks/whatsapp`, builder A): checked against `WHATSAPP_WEBHOOK_SECRET` (AiSensy's signature if its plan signs, else the secret in an `X-Webhook-Secret` header, compared in constant time over SHA-256 digests; proposed, §10), read as the WhatsApp Cloud API's body (`entry[].changes[].value.statuses[]` and `.messages[]`, which AiSensy forwards; to be confirmed on the plan), normalised to `WhatsAppNotice` (`src/lib/messaging/inbound.ts`): a status moves the message as above; an inbound message sets the person's `whatsappLastInboundAt` (found by E.164 mobile), and a plain stop (`isStopRequest`: STOP, Unsubscribe, Opt out) suppresses WhatsApp for that number and records a withdrawal of `marketingWhatsapp` if one is in force (channel WhatsApp, the provider's message id as evidence), the same day (`13` §7). The text is never stored. The out-of-hours reply ("we reply from 10 AM", once) is AiSensy's own setting.

## 6. Timing, rescheduling and cancellation

Timing rules are pure (`src/lib/automations/timing.ts`): `reminder24hAt`, `reminderShortAt`, `after`, with `06`'s offsets. A planner task writes the row at plan time with `sendAt` from the rule and `sendBefore` = the session's start; `plannedSendTime` applies quiet hours at planning, and `decideSend` again at sending. **Reschedule** (`booking.rescheduled`, new booking with `fromBookingId`): B5, B6 and B13 first `cancelQueued` the old booking's queued rows, then plan the new booking's; B7 tells both sides; M3's calendar job moves the event. **Cancellation**: every queued row about the booking is cancelled. **Belt and braces**: at send time `load` answers `stale` when the booking is no longer confirmed, has moved, or (B13's reminder) is paid, and the row is skipped as `stale`. A WhatsApp reminder due at 22:00 IST goes at 08:00 if that is before the session, else it is dropped.

## 7. Templates

**Registry** (`src/emails/registry.ts`): every Release 1 key with its automations, channels, sender, kind, footer link (`withdraw` page, `unsubscribe` with headers, or `none` for internal mail), `counsellingScope` (every booking template to the client, the money ones included; not the internal staff notice; `08` §7), `offers: false` for every one, and its price rule: `never`, `whenPublic` (the confirmation, the receipt, the refund and the slot-lost notice: the amount only while `prices_public` is on, each saying the same without it while prices are hidden) or `paymentLink` (the payment link staff send and its reminder: D-24's one exception, docs/16 §1). WhatsApp templates are the eight of `06` (`WHATSAPP_TEMPLATE_KEYS`), each naming the person's own booking; slot lost and the payment link's reminder go by email. Their texts for Meta are in `docs/content/whatsapp-templates.md`; the five about a booking's time end with one closing variable, the booking's reference, followed for a counselling booking by the scope and crisis line (`whatsappClosing`, `src/emails/booking/copy.ts`), so one approved text serves every booking and no variable is ever empty.

**Frame and parts** (`src/emails/components/`, ported from `src/brand/templates/email/booking-confirmation.html`): the paper page, the mark, the white card with the yellow bar, the footer with the legal line from Settings, the site and the preference link; `Paragraph`, `Button` (one per email), `Details` (the ticket), `CounsellingScope` (words from `src/lib/counselling/scope.ts`). Colours from `tokens.json` by role (`src/emails/palette.ts`). `renderEmail` (`src/emails/render.ts`) gives HTML with Outlook's 600 px ghost table and the plain-text part. The PNGs (`mark-email-160.png`, `logo-email-600.png`) are served from `<site>/email/`.

**Implementations** (`src/emails/types.ts`): per key a `load(req, { subject, recipient, sendBefore })` that reads the data at send time and validates it with the template's Zod schema, an `email` (subject, preheader, element) and, for the eight, a `whatsapp` (ordered params). Builder A fills `src/emails/core/`, B `src/emails/booking/`, C `src/emails/other/`; `src/emails/index.ts` joins the three maps. Words are in each template's file, `en-IN`, written to `VOICE.md` and checked with `/copy-check`; unknown facts are `[[TODO: …, I-xx]]` and block the send in production; an approved `message-templates` entry overrides the subject, preheader and lines. Subjects state the fact; no emoji, no urgency.

**What a template may not say**: no offer, bridge, story or cross-sell; for counselling, nothing about the session but its time, format, place or link and how to reschedule, plus the scope and crisis lines; no price outside its rule; no name of another client; nothing from a note.

## 8. The newsletter (D-10)

`subscribers` holds email (unique), status (pending · confirmed · unsubscribed), the notice shown, person, consent, source, confirmExpiresAt, confirmedAt, unsubscribedAt, lastEngagedAt and the hidden `confirmTokenHash`; owners and the office read it, the server writes it, owners delete. `newsletter-issues` holds number, title, preheader, the lead post with a note, up to two items, the call to action (a path on this site), status (draft · scheduled · sending · sent · cancelled), scheduledFor, sentAt and recipientCount; editors and owners write and schedule, the office reads.

Signup (builder C): a form on the Journal posts to `/api/newsletter` (Zod, rate-limited per instance by a hash of the client's address, a hidden trap field, Turnstile with M7; the same answer whether or not the address is known); the form is `SignupForm` in `src/app/(platform)/newsletter/`, shown on its own at `/newsletter` (where every newsletter form and link lands with its outcome) and placed on the Journal's pages at the join; a pending entry keeps the address, the notice in force and the hash of a 32-byte token for 7 days; N1 sends the link. `/newsletter/confirm/[token]` shows the notice and a button, and confirms on its POST to `/api/newsletter/confirm` (link scanners do not confirm): the consent `marketingEmail` is recorded first (channel web, the form, IP and browser, the notice from signup), then the person is found or added by email and the entry confirmed; `newsletter_confirmed` is counted; N2 welcomes. Unsubscribe: every promotional email carries one-click headers to `/api/newsletter/unsubscribe` (RFC 8058) and a visible link to `/newsletter/unsubscribe/[token]`; both record the withdrawal and mark the entry. The unsubscribe token is the core's signed link for `unsubscribe` naming the subscriber; a GET of the one-click address never unsubscribes, it shows the page. Transactional mail links `/w/[token]` (the signed link for `withdraw`, naming the person), the person's consents in force each with a withdraw button that posts to `/w/[token]/withdraw` (builder C). An editor drafts, schedules (a time from now on) and cancels an issue; only N4 moves it to `sending` and `sent`, and a sent issue no longer changes. N4 sends an issue at its time to every confirmed subscriber whose consent is in force then, one `messages` row each (variant `s<subscriber id>`), through Resend's batch endpoint from `news.` with click tracking on that domain only (proposed, §10); without the core it plans nothing and leaves the issue scheduled. A complaint or withdrawal unsubscribes at once (N3). Hygiene (`13` §6: twelve months without a click) waits until a subscriber is a year old.

## 9. Digests, reports and alerts

O1 (08:30 IST) goes to active owners and operators; O2 with O10 (Monday 09:00) to owners; both from `platform@`, in sections each module supplies as counts and booking references only, no client names (proposed): today's sessions by practitioner and time, time requests waiting, refunds awaiting approval, reconciliation mismatches, failed messages and jobs, suppressed addresses, reviews awaiting consent; M4 adds lead ages, M5 privacy deadlines and incidents. O2's metrics are `00`'s funnel from `analytics_events`, week on week; O10 adds the ten most-asked missing pages, the count of searches with no results, delivery per sending subdomain from `messages` (sent, delivered, bounced, complained), the WhatsApp quality rating and cost lines (both an owner's input until a source exists: placeholders). O3 shows failures on Today (M5 reads failed `messages` and failed jobs) and emails owners when three fail within an hour (failed messages, sends with no answer and jobs that spent their retries, counted together), at most once an hour: one row per active owner and hour, key `O3:users:<owner>:h<UTC hour>:email`. O3's own failures are counted but raise no `automation.failed`, so a failing alert never queues another.

## 11. The test plan

Unit (pure, no database): `decideSend`, `quietHoursEnd`, `plannedSendTime`, the state table and retry delays, `messageKey`, the timing rules, `parseResendEvent`, `isStopRequest`, `senderFor`, the catalogue against `06` (every R1 id once, a template for each messaging automation, tasks named by id, schedules in UTC), the registry's rules (no offers, scope on counselling templates, price rules, footers, the eight WhatsApp templates), the access table, the environment, the frame's render (written). Each builder adds its own. Integration (Postgres, fake senders, a fixed `now` passed in), one file per automation group, each proving the five properties:

- **Fires once**: emit the event twice and run the queue twice: one job ran its work, one `messages` row, one fake send; a replayed webhook changes nothing.
- **Right time**: the row's `sendAt` equals the rule; dispatch a minute before sends nothing, at the time sends it; B5 is not planned for a booking made 20 h ahead.
- **Right channel**: WhatsApp when configured and approved; with WhatsApp `not-configured`, suppressed or unapproved, one email row with `fallbackOf`; internal mail from `platform@`.
- **Consent**: a promotional message without consent, or with consent withdrawn after it was queued, is skipped `no-consent`; an under-18 person gets nothing promotional; transactional mail needs no consent.
- **Quiet hours**: a WhatsApp reminder due 22:00 IST is sent at 08:00; a B6 that 08:00 would put after the start is skipped `quiet-hours-late` (`13` §10's launch check); email is not held.
- **Re-planning**: reschedule cancels the old booking's B5 and B6 rows and plans the new booking's at the new times; cancellation cancels them; a stale row is skipped at send time.

Routes: the cron route refuses no secret, a wrong secret and a preview; the Resend route refuses a bad signature and suppresses on a signed permanent bounce; the WhatsApp route honours STOP. e2e (desktop and 375 px, axe): the newsletter signup, confirmation and one-click unsubscribe. The rendering matrix (`13` §5): Playwright renders each template at 320 and 700 px with images off and runs axe on it; the seed test on Gmail, Outlook, iPhone and Yahoo is a person's, per release (`13` §6).
